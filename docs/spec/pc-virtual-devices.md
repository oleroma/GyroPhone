# PC: virtual devices

How a STATE becomes input a game sees. Over Bluetooth the phone is itself a HID device ([Connection](phone-connection.md)); this page is the companion's side.

## Game pad (ViGEm)

`GyroPhone.Windows/ViGEmPadSink.cs` plugs a virtual pad through the **ViGEmBus** driver (installed by the person; Home and the Gamepad page say when it is missing, with Retry):

- **Xbox 360** (XInput, the default) or **DualShock 4** (DirectInput HID), chosen in the tray or the Gamepad page; **Off** plugs nothing (keyboard and mouse only).
- **When the pad is plugged**: at a session's start, on a pad thread outside the engine lock (plugging blocks in the driver), so the session's first STATEs go on with keys and mouse at once and skip the pad until it is in; then the newest STATE goes to it and a HOST_STATUS says PAD_PLUGGED. When a session ends (BYE, the 10 s timeout) the pad **stays plugged** at rest (buttons up, sticks centred, triggers 0, gyro still), so the game keeps its controller (the same XInput slot, the DualShock 4 / DualSense gyro it found at start) and the next session in the same output mode reuses it. It is unplugged when the output mode changes (and plugged in the new mode on the pad thread when a session is up; the menu never waits), when the phone of the last session is forgotten (forgetting another phone keeps it), on exit, and after **5 minutes** with no session.
- `GyroPhone.Protocol/Mapping/PadMapper.cs` maps STATE to the report: the 16 phone buttons and hat to XUSB bits or DS4 buttons/special/hat, sticks signed (+Y up for X360, bytes with 128 = centre for DS4), triggers 0..1023 to bytes. Buttons X360 can't show (M1–M4, Share) are logged once.
- Reports are built whole and sent with one SubmitReport, only when the mapped frame changed. The DualShock 4 always gets its full report (`Ds4Report`, ViGEm's DS4_REPORT_EX via SubmitRawReport): buttons and sticks plus gyro, accelerometer, a timestamp, battery on cable and an untouched touchpad. ViGEmBus before 1.17 lacks that report: the DualShock 4 then gets the simple one (buttons, sticks, triggers, no motion) and the log says to update ViGEmBus.
- **DualShock 4 motion**: while the pad is a DualShock 4 the phone sends MOTION ([Protocol](protocol.md)) with its raw gyro and accelerometer, whatever the workspace's own gyro does. `Ds4MotionFeed` turns each new sample into its own report with the pad's current buttons and sticks, stamped with the sample's own time (16/3 µs units; the DualSense, below, gets the same samples; samples lost beyond the 8 a packet repeats still count their time, from the phone's times, up to 1 s), so games that read the pad's gyro (The Finals, Steam Input) add up the turn exactly. Input not allowed on the phone, the companion paused or locked, or no MOTION for 60 ms: the gyro rests (the accelerometer keeps its last reading). Turn the app's gyro mouse off in a workspace whose game aims with the pad's gyro, or both move the camera. The phone maps its axes to the pad's first (`PadGyro`, the workspace's PC pad yaw / pitch / roll settings; default: the screen is the pad's face). Games check for gyro when they start, so start the game after the phone connects. A broken bus is retried at 10 Hz. A pad removed underneath (driver reset, disabled) is plugged again by the pad thread, never on the input path: keys and mouse go on meanwhile, and a failed plug is retried after 1 s, then less often, up to every 10 s.
- **Rumble** from games is recorded on the driver thread and sent as RUMBLE at most 100 Hz. The phone vibrates with it while its **Vibrate with game rumble** setting (Settings → Vibration, on by default) is on. The DualSense output doesn't pass rumble on yet.
- The virtual pad's XInput slot is reported, so the PC-controller reader skips it.

## Game pad (DualSense, optional driver)

`driver/` is the optional **GyroPhone pad driver**: a user-mode (UMDF 2) driver on Windows' Virtual HID Framework that shows a wired **DualSense** (054C:0CE6, the real HID descriptor, answers to the calibration, pairing and firmware feature reports). ViGEmBus can't do a DualSense. See `driver/README.md` for install, uninstall and risks.

- Installed by the person with `driver\install.cmd` (after a PC build the install hook copies the package, unzipped, into the repo's `build\GyroPhonePad-driver`; it never installs it. The zip is only for releases): it makes a signing certificate for that PC only, trusts it there, signs the package and installs it on a `Root\GyroPhonePad` device. Test signing stays off. `uninstall.cmd` removes all of it.
- `PadSinks.Create` gives the engine a `CombinedPadSink` when the driver's device interface is there: ViGEm for Xbox 360 / DualShock 4, `DualSensePadSink` for **DualSense**. The DualSense choice shows in the tray and the Home and Gamepad pages only then (restart the companion after installing). The driver is looked for at start and on "Try again".
- The DualSense takes the DualShock 4's frame (`PadMapper.ToDs4`, the same buttons), built as report 0x01 by `DualSenseReport` and sent with one DeviceIoControl per change. A pad belongs to the companion's handle and goes when it closes.
- **Motion**: the DualSense gets the same MOTION as the DualShock 4 (the phone sends it for output modes 2 and 3), one report per sample through the same `Ds4MotionFeed`: gyro at bytes 16..21, accelerometer at 22..27, in the DualShock 4's units (the driver's calibration report says so), and the sample's own time at 28..31 in 1/3 µs, the DualSense's sensor timestamp. The feed keeps one clock in 1/3 µs; the DualShock 4's 16/3 µs timestamp is every 16th tick of it. The workspace's PC pad yaw / pitch / roll settings apply to both.
- **Not yet**: touchpad, rumble, lightbar and adaptive triggers. Output reports are accepted and ignored.

## Keyboard and mouse (SendInput)

The default, and the fallback without the optional input driver (below).

`GyroPhone.Windows/SendInputSink.cs`, one SendInput call per injection:

- `InputDiff` diffs what was injected against the new STATE: modifier downs, key downs, mouse buttons, key ups, modifier ups, move, wheel, horizontal wheel. Releases mirror presses: a Ctrl + click lets go of the button before Ctrl, and releasing everything lets go of mouse buttons first.
- Keys go as **Set 1 scan codes** (`HidScanCodes`, from HID usages), so games that read scan codes work; Pause and the media keys go as virtual keys. Unknown usages are counted, never injected.
- Mouse moves are relative, from the difference of STATE's cumulative totals (`MouseDeltaTracker`), each step capped at 16384; after lost or late packets the missed stretch catches up over up to 16 ms (App page › **Catch-up time**, Off / 8 / 16 / 32 ms) while new motion still goes out at once, so the cursor travels through it instead of jumping (`MouseCatchUp`); buttons L, R, M, Back, Forward.
- Wheels in 1/120 notch when the session has HIRES_WHEEL (STATE_HIRES), else whole notches.
- **Key repeat** (`KeyRepeat`): held Volume Up/Down repeat after 400 ms every 50 ms, because Windows doesn't repeat injected keys.

## Keyboard and mouse (input driver, optional)

`input-driver/` is the optional **GyroPhone input driver**: a user-mode (UMDF 2) driver on Windows' Virtual HID Framework that shows a **USB mouse, keyboard and media keys** (one HID device, three top-level collections, `VID_1209&PID_6770`). Separate from the pad driver: its own package (`GyroPhoneInput-driver`), INF, `Root\GyroPhoneInput` device and device interface, installed and removed on its own. See `input-driver/README.md` for install, uninstall and risks.

- **Why**: SendInput returns only after Windows ran every program's input checks; with a game open about 1 call in 600 waited 3–8 ms. A report to the driver returns at once (Windows runs those checks later on its own input thread, as for a real mouse), and Windows sees real device input, not input marked as injected. Input also reaches elevated windows. Diagnostics' delivery probe ([Companion](pc-companion.md)) measures what a game reading raw input gets either way.
- **Why it's off by default** (event trace 2026-11-15, Windows 11 25H2, Delivery test in front): the driver itself hands a move to Windows in about 0.1 ms every time, but Windows 11 processes a HID mouse's moves on dwm's input thread, and that thread waits whenever another program (Chrome, Steam, Discord, Explorer, the companion's own window…) holds Windows' shared window lock (the win32k user critical section). So about 1 move in 400 waited over 4 ms and the worst 21 ms. SendInput posts the move to the window in front from GyroPhone's own thread and only then waits for dwm (worst 3.4 ms, none over 4 ms). Pauses before a move made no difference.
- **Install**: `install.cmd` as the pad driver's (after a PC build the install hook copies the package into the repo's `build\GyroPhoneInput-driver`; it never installs it). Both drivers use this PC's one signing certificate ("GyroPhone pad driver (this PC only)"): whichever is installed first makes it, and each `uninstall.cmd` keeps it while the other driver's device is there.
- **Route** (`KeyMouseRouter`, the engine's `IKeyMouseSink`): SendInput, unless **Use input driver** (Performance, off by default, `HostSettings.UseInputDriver`) is on and the driver is installed with its devices plugged. While Use input driver is on, the companion plugs the devices once it owns the port (an instance on its way out may still hold them) and looks again every 5 s from the UI timer (installed later, or back after it went away), off the input path. Off, it unplugs them, so no idle virtual mouse and keyboard stay in Windows and nothing holds the device open (uninstall.cmd can then remove it without a restart; it asks to quit the companion first). Switching the route (Use input driver, the driver found or lost) lets go of every key and button first, under the engine lock; the next STATE presses what is held again. The devices belong to the companion's handle: closed or crashed, they go away and Windows lets go of what they held. A failed submit (device gone) unplugs the sink and returns false, so the engine sends the held set again through SendInput.
- **Reports** (`HidInputReports`, the same layout as `input-driver/src/gpinput_reports.h`): mouse 1 (buttons L R M back forward, X, Y, wheel, horizontal wheel, int16), keyboard 2 (one bit per usage 0x00–0xE7, the same bitmap as STATE's keys, any number at once), media 3 (play/pause, previous, next, mute, volume up, down: the usages `HidScanCodes` sends as virtual keys). A report holds the whole state, so one hand-off is usually one mouse report; a new report starts only where merging would change what Windows sees (a key or button changing twice, a modifier going down before the keys it shifts and up after them, a move before a click, a switch between keyboard and mouse with presses pending). All of a hand-off's reports go in one DeviceIoControl, straight to `VhfReadReportSubmit` in the driver (no queue or thread of ours); preallocated buffers, nothing allocated per packet.
- **Own container**: the driver's device says it's removable, and the mouse and keyboard carry their own container id (`GpiContainerId` in `driver.c`), so Windows takes them for a separate box, like a plugged-in USB mouse. Without it they counted as part of the PC, and Windows dropped their left clicks while any key was held, its guard against palms on a laptop touchpad while typing (seen 2026-11-15 on Olex's laptop; right clicks, keys, SendInput and an external USB mouse were unaffected). The container id alone wasn't enough: Windows kept the devices in the PC's container while their parent was in it.
- **Wheels** carry a resolution multiplier (feature report 1, 1 or 120): Windows sets it to 120 when the mouse appears, so one count is 1/120 notch, as WHEEL_DELTA. Until it does, the driver adds the 1/120 steps up and sends whole notches.
- **Differences from SendInput**: held keys auto-repeat like a real keyboard's (Windows' typematic; KeyRepeat's extra volume downs change nothing in the report); input reaches elevated windows (the engine's UIPI handling then has nothing to resend); Pause goes as keyboard usage 0x48.
- **Raw input readers** skip the driver's own devices as they skip SendInput's input (`OwnInputDevice`, by device name): "Press a key" never takes GyroPhone's output for a PC key; the delivery probe and the video latency test tool's bar (`tools/latency-test`) count them as GyroPhone's.

## PC gyro mode

When the phone's **Use PC controller for gyro ratchet** is on ([Controllers](phone-controllers.md)), STATE_GYRO carries raw samples and the gyro config. The engine:

1. reads the PC's controller (`XInputPcPad`: the first XInput pad that is not ours, every millisecond on its own thread, counting presses so none is lost between STATEs; empty slots checked only every few seconds);
2. works out each sample's ratchet state from what was held **at that sample's time** (`PadHeldHistory`) and the PAD_GYRO buttons (`GyroGate`: axes each ratchet flips, toggle, own settings from PAD_GYRO_SET);
3. runs the samples through `GyroMath.cs` (the exact port of the phone's `GyroMath.kt`), and fills a gap longer than the 8-sample ring in one step from the running totals;
4. adds the result to STATE's non-gyro mouse, wheel and pad axes before injecting.

The PC controller's own buttons still reach games directly (or through Steam Input); the companion only reads it. Its ratchets also count for the overlays' "Ease on ratchet".
