# PC: companion app and tray

The Windows companion (`GyroPhoneCompanion.exe`) receives the phone's Wi-Fi/USB link and turns it into a virtual game pad, keyboard and mouse, and draws the overlays. Bluetooth needs no companion. Projects in `companion/src/`:

| Project | What it is |
|---|---|
| `GyroPhone.Protocol` | Wire format, crypto, STATE to pad and SendInput mapping, gyro math port. Cross-platform, unit tested. |
| `GyroPhone.Host` | The protocol engine (`HostEngine`), UDP server, sessions, pairing, settings, key files, link stats, overlay pose. Cross-platform; all I/O behind interfaces in `Abstractions/`. |
| `GyroPhone.Windows` | Windows sinks and probes: SendInput, ViGEm, XInput PC pad, AOA USB, firewall, DPAPI, autostart, MMCSS, power QoS, logs. |
| `GyroPhone.Tray` | The exe: tray icon and menu, overlays, watcher, updater. WinForms + Direct2D (Vortice). |
| `GyroPhone.Ui` | The WPF main window and pairing window, reached through `ICompanion`. |
| `GyroPhone.Headless` | A console host for Linux/testing (`--pair`, `--no-vigem`, `--latency-csv`). Not shipped. |

.NET 8, published self-contained, single file, win-x64.

## Two processes

The one exe runs as two processes, so nothing the windows do (WPF and WinForms, the overlays' drawing, a window that hangs, their memory cleanups) can pause the input:

- **The input process** (`GyroPhoneCompanion.exe --input`, `InputHost`): no window, no tray, never loads WinForms or WPF. It runs the phone link (UDP and the cable), the engine (mappings, injection, the virtual pad, the input driver), pairing keys, the held-keys marker and Diagnostics' delivery probe, at **High** priority class, with a large young-object budget (`DOTNET_GCgen0size`, 64 MB) so memory cleanups stay rare. Only one runs per Windows session (`Local\GyroPhoneInput`). It keeps `settings.json`.
- **The companion** (the control panel, `TrayApp`): the tray, all windows, the overlays, the Performance page, pairing's windows and Diagnostics' log. It starts the input process and keeps `companion.json` (overlays, presets, shortcuts, Fade when phone rests, tray click; made from `settings.json` the first time).

They talk two ways, and neither ever waits on the other on the input path:

- **A pipe** (`PipeChannel`, `GyroPhoneInput.<user>.<session>`, open only to this Windows user): the companion's commands (`IInputControl`: output mode, pause, pairing, USB, Diagnostics and the rest, each answered at once), and the input process's events, sent from its own thread (`EventOutbox`, gp-events): its status (`InputStatus`, at most 10 a second and once a second), Diagnostics' notes, each second of the link for Performance, pairing prompts.
- **Shared memory** (`SharedRegion`, `Local\GyroPhoneShared`): the overlay packets as they came (`OverlayInbox`, the ring gp-rx copies into, waking the companion's gp-overlay through `Local\GyroPhoneOverlayWake`), the held outputs and the PC controller for the Fire and Aim displays (`HeldMirror`, a sequence lock), and Diagnostics' raw events (`DebugQueue`), which the companion turns into text.

**The Rust input program.** The input process exists twice: the original one in C# (`InputHost`) and one written in Rust (`companion/src/input`), which does the same job the same way: the same packets, pairing, sessions, engine, outputs, pipe, shared memory, files and log lines. **Use the Rust input program** on Performance › Input program (default off, the companion's own setting `HostSettings.RustInput` in `companion.json`) chooses which one the companion starts; the card says which one runs now. Switching tells the running one to exit (it lets go of everything held and says goodbye to the phone) and starts the other: the phone reconnects within a second or two. The Rust program is a library, `gp_input.dll`, that rides inside the exe: `GyroPhoneCompanion.exe --input --rust` (`RustInput`) unpacks it next to the exe as `gp_input-<version>.dll` (in `%LOCALAPPDATA%\GyroPhone\bin` when that folder can't be written; older builds' files are removed), loads it and hands the process over to it. So the process is still `GyroPhoneCompanion.exe`: the firewall rules, the place on disk and the admin rights are the same as the original's. .NET stays loaded in it but idle: every thread that carries input is Rust's own, which .NET never pauses, and nothing on the play path asks for memory. Its version ends with `+rust` (`0.1.<build>-<commit>+rust`), which is how a companion tells the two apart; one that finds the other program attached replaces it. A Rust input program that can't start, or stops within 30 s, three times in a row is given up on: the companion starts the original one, turns the switch off and says so on the card, in a tray notification and in the log. When the Rust program hits an error it can't go on from, it lets go of everything held first, writes the log and ends; the companion starts it again like any input process that went away. A build made where Rust isn't installed has no Rust program: the switch is greyed and the card says so. The C# input program is kept as the fallback.

**Replay files.** `companion/tests/replay/v1` holds six made-up play sessions (keys and mouse, the Xbox pad, the DualShock with motion, the PC gyro, a rough link with lost, repeated, damaged and foreign packets, and pairing done right and wrong), each as the engine's inputs (packets, ticks, the companion's calls) with what the C# engine did after each: key and mouse events, pad reports, packets back to the phone, log lines. The C# test (`ReplayCompareTests`) makes each session again and compares it with its file; the Rust test (`tests/replay.rs`) feeds the same inputs to the Rust engine and must get the same outputs, byte for byte and in the same order (log lines and the pairing prompt are compared as their own stream). A change to the C# engine that changes what it does shows in the C# test: write the files again with `GP_REPLAY_WRITE=1` and port the change until the Rust test passes.

**Exit and crashes.** Tray **Exit** (and an update or Restart as administrator) stops both: the input process lets go of everything, says goodbye to the phone and saves, and the companion waits for it before exiting. When the input process goes away by itself, the companion starts it again within half a second (every 10 s after five in a minute) and the new one lets go of what the old one held (the held-keys marker); the tray says "Input restarting…" meanwhile. When the companion goes away by itself, input keeps going and starts it again 2 s later (once a minute after more than five within 10 minutes, so a companion that keeps crashing doesn't load the PC; `--reattach`); the new companion picks up the overlays, though a pointer's layout shows only once the phone sends it again. A companion that finds an input process of another build (or not elevated while it is) tells it to exit and starts its own.

## Threads and timing

- **gp-rx** (`UdpHostServer`): the one UDP socket on port **47800**. Blocks in ReceiveFrom, drains the backlog into `HostEngine.OnDatagram`, then `Flush` injects once, so a burst of STATEs makes one injection. A STATE whose keys or buttons differ from the one before it injects that earlier one first, so no press is lost; a pad button pressed and released inside one burst stays visible for 20 ms for polling games. Registered with MMCSS ("Games", high) and opted out of power throttling (`Mmcss`, `PowerQos`). No timer resolution change. While a lost or late stretch of mouse motion catches up it also wakes every millisecond without packets to move it on: on Windows by waiting on the socket's read event and a high-resolution waitable timer together (`ExactCatchUpWait`; WSAEventSelect for the wait only, the socket stays blocking otherwise), since a plain socket.Poll timeout only ends on the 15.6 ms system tick; a datagram still wakes it at once.
- **gp-watchdog** (`Watchdog`): its own thread at AboveNormal priority, ticking every 50 ms on a high-resolution waitable timer, for `HostEngine.OnTick`: releases everything after **250 ms** without a STATE, drops a session after 10 s, expires pending sessions (2 s), runs pairing timers and sends HOST_STATUS once a second. While nothing needs it (no session or pending session, no pairing or QR code, no Link test, nothing held), it ticks only about every 300 ms, and a session starting brings the 50 ms tick back at once. The tick does only in-memory work. Environment probes (1 Hz) go to the thread pool.
- **gp-keepawake** (`Watchdog`): an AboveNormal thread that sends the phone a tiny sealed KEEP_AWAKE every **10 ms** while a session runs with the PC as a Wi-Fi client (not over USB, Ethernet or loopback; no setting). The watchdog's probe looks up the PC's adapter on the phone's subnet every second (`LinkPaths.AdapterFor`, `HostEngine.SetPcAdapter`): when it is a network cable or the Mobile hotspot's own adapter, none is sent, since no radio of the PC dozes there and the packets would only keep the phone's Wi-Fi awake. Only the adapter's kind decides (a Wi-Fi card on a router that uses 192.168.137.x still gets them), the answer holds only for the phone address it was found for, and while the adapter isn't known (not found, a new session's first second) they are sent. A Wi-Fi client in power save wakes only at each beacon, about every 100 ms, so while the phone sends little (held still) its packets would reach the PC in 100 ms batches; the steady traffic keeps the PC's radio awake. While none is wanted (no phone connected, a wire, or a PC that is no Wi-Fi client) it rests instead of waking every 10 ms, until a session starts or a LINK_INFO comes (looking again every second). It takes no engine lock.
- **gp-save** (`Watchdog`): a BelowNormal writer thread that, every 500 ms, writes the held-keys marker if the held set changed and settings if anything changed (all changes since its last turn in one write; a failed write is retried after 1 s). A slow disk or a virus scan never holds up a tick, and never runs on gp-rx.
- **gp-usb-rx / gp-usb-tx** (`UsbBridge`) for the direct cable: every packet passes through them before gp-rx, so they get the same MMCSS ("Games", high) registration and power-throttling opt-out.
- **gp-overlay** (`OverlayWorker`, AboveNormal, in the companion): everything the phone sends for the overlays. gp-rx (in the input process) only copies each OVERLAY, OVERLAY_SAMPLES and OVERLAY_LAYOUT as it came into a fixed ring (`OverlayInbox`, 256 preallocated slots, nothing made, nothing waited on; full: the newest is dropped; in shared memory) and wakes gp-overlay once the input is handed off. gp-overlay turns each overlay window's pose, keeps "Fade when phone rests", the Speed graph and the layout, and publishes them for the windows. It works on its own copies of the overlay settings, handed over whole when they change; what Level and Set orientation change in them is saved by the companion. The PC controller's gate for the overlays (its axes and ratchets, which are the input's) is worked out by gp-rx and passed along with the frame. Without the thread (tests, the headless host) the same work runs inline.
- **Overlay pacer** and the UI thread ([Overlays](pc-overlays.md)).
- **gp-press-listen** (`RawInputListener`): only while the phone's "Press a key" listens (CAPTURE): a hidden message-only window reading the keyboard and mouse through raw input (RIDEV_INPUTSINK). It only reads, so every key and click still reaches Windows and the game; keyboard input with no device behind it (SendInput, ours too) is skipped. The PC controller reader (`XInputPcPad`) runs meanwhile too. `PressCapture` turns both into CAPTURED on the watchdog's tick. Each time it starts, the tray shows a Windows notification, **"Press a key or button"**, so you know keys, mouse buttons and controller buttons on the PC count too (`HostSnapshot.Capturing`). The App page's **Press a key** card has **Use this PC's keys for Press a key** (on by default; off, CAPTURE is ignored and the PC is never read, and turning it off while the phone listens stops at once; `HostSettings.PressKeyListen`) and under it **Notify when the phone listens for a key** (on by default; `PressKeyNotice`). Mouse buttons count even with no device behind them, since a laptop's precision touchpad sends its clicks that way (GyroPhone sends no clicks while the phone listens); keys with no device (SendInput) are still skipped.
- **gp-log** (`FileLog`, Normal priority): writes the log files. `Write` only puts the line in a lock-free queue and wakes it, so no thread ever waits on it.

All engine state is under one lock, which gp-rx takes for every packet and Flush. So that a thread Windows pauses while holding it never keeps gp-rx waiting, everything read many times a second is read without it: when a locked call ends, the engine copies what changed into a published view (`OverlayView`, a sequence lock: readers copy and retry if a write came in between, the writer never waits), and the overlay windows (newest OVERLAY and layout, each window's pose, "Fade when phone rests", the Fire and Aim displays' outputs, Connected), the held-keys marker and the catch-up flag read only that. The PC controller's state comes from its reader thread's own published copy (`IPcPad.Peek`). The overlay part of the view has its own sequence lock and writer (gp-overlay); gp-overlay is woken after the Flush, and the laser outputs are published after the hand-off, so overlays never delay input.

**No new memory on the input path.** Everything gp-rx uses per packet is made once and reused, so .NET never has to stop the program to clean up after it. `ZeroAllocationTests` plays a few thousand STATEs, pings, link info and overlay packets through the engine (with and without Diagnostics) and fails if gp-rx made a single byte of new memory. `Snapshot` (tray and main window) only copies plain values under the lock (the paired phones list is kept ready), and settings are turned into JSON after the lock is let go (a change made meanwhile is saved on the next tick). The pad driver and SendInput calls stay under the lock, as they decide what the engine counts as held. Engine callbacks only post to the UI thread.

## Sessions and safety

- One **active session**; a new one replaces it only when its first valid STATE arrives (`SessionManager`), and the old phone gets HOST_BYE REPLACED.
- **Release-all** on silence (250 ms), session end, Pause, workstation lock or suspend, exit, and session switch.
- **Crash safety** (`HeldKeysMarker`): while anything is held, `%LOCALAPPDATA%\GyroPhone\held.json` lists it (written by gp-save within half a second of a change, and on exit); the next start releases what it lists and deletes it.
- **UIPI**: when an elevated window is in front or the secure desktop is up, SendInput drops events; the engine notices, and once input goes through again re-sends the ups and then the downs of what is held, so Windows' key state matches. Home warns, with **Restart as administrator**. The companion only checks its own token, never opens other processes (anti-cheat logs that).
- **Pause input** (tray, Gamepad page): releases everything; STATEs keep updating the baseline but inject nothing.

## Tray

`TrayApp`. Left click opens the main window (App page: or pairs a new phone). The right-click menu is short, the everyday switches only:

- the version, a status line, and a problems line that opens Home;
- **Open GyroPhone**, **Pause input**;
- **Gamepad output** ▸ Xbox 360 (default) / DualShock 4 / Off (keyboard and mouse only);
- **Overlays** ▸ one switch per window, Hide all overlays (Ctrl+Alt+O), Edit: drag the windows to move and resize (Ctrl+Alt+E), All behind: the game covers them, OBS still records them (Ctrl+Alt+B), Level all: as held now shows face-on (Ctrl+Alt+R), Overlay settings…;
- **Pair new phone…**;
- **Exit**.

## Main window

`GyroPhone.Ui/MainWindow.cs`, a sidebar of pages, refreshed twice a second. A page is built the first time it is shown, only the page on screen is refreshed. A change made on a page (a slider step, a toggle) refreshes only that page at once; the tray and Home follow 250 ms after the changes stop, and an overlay draws the change at its next frame.

- **Home**: a warning bar per problem with its fix (no ViGEmBus, firewall, Public network while no phone is seen, input blocked by an elevated window…), then cards: phone, link (only the way its packets go, such as "Phone hotspot · PC Wi-Fi"), gamepad (output, pause); full status under Details. Link numbers and latency are on Performance.
- **Phones**: Pair new phone, paired phones (each with Forget), this PC's key.
- **Gamepad**: output Xbox 360 / DualShock 4 / Off, Pause, the ViGEmBus driver state and Retry.
- **Overlays**: see [Overlays](pc-overlays.md).
- **Connection**: network category, firewall and USB checks with their fixes, the USB cable (direct cable on/off, default off), the server's port and addresses.
- **Performance**: everything measured and every speed setting: the phone link live with latency, Diagnostics (see [Performance](#performance)), Mouse (**Catch-up time**: Off / 8 / 16 / 32 ms, default 16, `HostSettings.CatchUpMs`; the longest a lost or late stretch of mouse motion is spread over, Off = the old one-step jump), **Keyboard and mouse** (which way keys and mouse go: SendInput, or the optional input driver's virtual USB mouse and keyboard, [Virtual devices](pc-virtual-devices.md#keyboard-and-mouse-input-driver-optional); **Use input driver**, default off, `HostSettings.UseInputDriver`, shown only while the driver is installed, sends through the driver instead of SendInput (off by default because Windows can hold the driver's moves up to ~20 ms, [Virtual devices](pc-virtual-devices.md#keyboard-and-mouse-input-driver-optional)) and lets go of every held key and button when switched; **Delivery test**, see [Performance](#performance)), **Input program** (**Use the Rust input program**, default off: which of the two input programs runs, see [Two processes](#two-processes); the card names the one running now), and Log (where `companion.log` is, Open log folder).
- **App**: Startup (Start with Windows, default off; **Start when my phone appears**, the watcher), Tray icon click (Opens this window / Pairs a new phone), Press a key, About (version).

**Scrolling** (`WheelScroll`, every window): the wheel and the touchpad scroll like a web browser. Each wheel message moves the page in proportion to its size: a whole notch is 100 px at Windows' usual 3 lines a notch (as Chrome; it follows that setting, and "one screen at a time" scrolls most of a screen), eased in over a few frames; a touchpad's small steps move it at once, so the page follows the fingers. The innermost scrollable area under the pointer that can still move that way takes it, so a table that scrolls only sideways (Performance's Results) passes the page's scrolling on, and a list at its end passes it to the page. Shift + wheel and the touchpad's sideways swipe scroll sideways. Item-based lists keep WPF's own scrolling.

**Pairing window** (`PairWindow`): a QR code for the phone's Scan QR code (a one-time token, renewed when it expires, gone when the window closes; holds up to four of this PC's IPv4 addresses), and for code pairing the PC's name, addresses, port and the pairing countdown, then "Pair <phone>? Code 123 456" with **Allow** / **Deny**. On first run with nothing paired the pairing window opens by itself.

**Diagnostics** (Performance, default off, `HostSettings.Diagnostics`, kept across restarts): one switch for every log, the same on the PC and the phone and kept in step. On, everything logs at once into memory: on the PC the engine's events (each STATE's presses and what they sent, each injection and pad frame, link and session changes; `DebugTrace`), the input recorder's lines and `sec` line (below), the PC's load each second with the program in front and the link's path (`PerfMonitor`), one line per .NET memory cleanup (garbage collection) in the companion: `memory cleanup 1.23 ms: gen 0, blocking, why: new memory, heap 312 MB, started by window thread` (how long it stopped every thread, its generation, blocking or background, why it started, the heap after, and the thread that started it: gp-rx, gp-overlay, gp-usb-rx, the window thread, or a thread number; `GcWatch`, the runtime's own GC events, switched off with Diagnostics), the phone's numbers each second (PHONE_STATS) and each open overlay's draw times once a second while they draw (every 30 s while idle; `OverlayTiming.On`); on the phone its own side ([Pad UI](phone-pad-ui.md#diagnostics)). **Keep** (1 to 30 minutes, default 3, `HostSettings.DiagnosticsMinutes`) is how much a Save covers (at most since it came on); the rings hold up to 30 minutes either way (200,000 events; the timelines 31 minutes). **Save** (or the phone's Save) writes this PC's events to `Documents\GyroPhone\Debug\pc-<time>.txt` (newest 20 kept; **Open debug folder**) and adds a record of the kept minutes to Results (link seconds, phone seconds, load, path: what the timed Record test kept, without the game's frames), and the phone saves its side at the same moment; `tools/debug-collect.sh` merges the two. The save's header has a `connection:` line (built only at Save, `LinkPaths.Connection`): the phone's side and the setup (Router Wi-Fi with band and channel, PC hotspot, USB cable direct or tethering, Ethernet on the phone, Phone hotspot), the Wi-Fi network's name when the PC is on that Wi-Fi itself (read from the Native Wi-Fi API; on the PC's own hotspot it says so), the PC adapter that receives the phone's packets with its description and the PC's address there, and the phone's address. The `link:` line shows the phone's signal only on Wi-Fi. Logging never changes what it measures: the input path only stores raw numbers in a preallocated queue (a slot written under a short lock; when it is full the newest slot is overwritten and counted as dropped in the save's header), and a timer drains it into text every 50 ms off the input threads. **Delivery probe** (`DeliveryProbe`, Windows, only while Diagnostics is on): its own thread reads raw mouse input (RIDEV_INPUTSINK on a hidden window; read-only, nothing held back), and matches each move from GyroPhone (no device: SendInput; or the input driver's own mouse: its raw device carries the driver's own container id, since a virtual HID device's name carries no vendor or product id; `OwnInputDevice`) to the run of moves in a row the engine stored at their hand-offs that adds up to it (`HostEngine.MoveSent`: Stopwatch ticks and size into a preallocated ring, no lock or allocation on the input path), timed from the newest move of the run. Windows 11 merges a real device's moves for background raw input readers like the probe (at most about 125 a second; the game in front still gets every report), so on the input driver one raw move usually carries several of GyroPhone's; SendInput moves come one by one. A raw move that matches nothing yet waits up to 50 ms for its hand-off to be stored. So SendInput and the input driver compare by when a game reading raw input gets the move, not only by how long the call took. A process has one raw mouse target: while "Press a key" listens it has it (the probe neither takes nor removes it meanwhile, `RawMouseOwner`), and the probe takes it back when it lets go. While Diagnostics is on, each raw move over 2 ms also gets its own line, made on the probe thread (at most 20 a second; the rest are counted as `slowlines-skipped N` in the `delivery[...]` text): `delivery slow 3.42 ms (driver): gap 12.0 ms since the move before, merged 3, front Discovery, probe slept 11.8 ms, read 0.02 ms after waking, 1st since waking` (its delay; the time from the move before's hand-off to this one's, so sparse moves show; GyroPhone moves that came inside this raw move; the program in front; how long the probe thread had been waiting for messages before it woke, how long after waking it read this move, and how many messages it had handled since waking). **Delivery test** (Performance › Keyboard and mouse, `DeliveryTestWindow`, companion process): a plain Win32 window on its own normal-priority thread that reads raw mouse input as a normal reader in front, like a game (no RIDEV_INPUTSINK, so Windows hands it every report, never merged), and times each of GyroPhone's moves from its hand-off to this window reading it. While it is open the input process also stores each move in the shared memory (`MoveRing` in `SharedRegion`, layout 2; no lock or allocation on the input path) and runs the delivery probe even with Diagnostics off, which adds up the test's moves too; the window shows both readers side by side (slow per 1000: over 2 ms; p99; max; moves that never came), counting only while it is in front (clicking elsewhere pauses it). Closing it stops everything and writes one summary line to `companion.log` (and Diagnostics while on). With Diagnostics off and no test open, nothing is stored or read. Both readers pair raw moves with GyroPhone's the same way (`DeliveryMatcher`). Off, nothing is queued, kept or measured, and the overlays don't add up their draw times. While on, the FPS overlay shows "● DIAG" with the link's last 60 s ([Overlays](pc-overlays.md)) and the phone's pad a red dot. No other log or metric runs in the background: each one only while its page or overlay is shown, Diagnostics is on, or a test runs.

**Phone and PC in step**: the phone's switch rides LINK_INFO's DEBUG_TRACE flag and the PC's HOST_STATUS flags2 `PC_LOGGING`; each side follows the other's when it changes, and when a session starts "on" wins on either side, so it stays on across reconnects. A Save bumps a 3-bit counter (the phone's in LINK_INFO flags `0x70`, the PC's in TEST_MODE `0x70`) and the other side saves too. While on, the PC sets TEST_MODE PHONE_STATS so the phone sends its numbers each second. Keep is per side.

**Overlay drawing threads**: the pacer (`OverlayPacer`) wakes every open overlay window at each screen refresh (20 times a second while none is busy, [Overlays](pc-overlays.md)), and each window draws on a thread of its own (`OverlayForm.Signal`, "overlay <id>", BelowNormal; the overlays' work on the graphics chip is set below normal too, `GpuDevice.LowerGpuPriority`: on a busy PC the game and the input go first and the overlays drop frames first), so windows draw side by side and a heavy one (a pointer's paint) never holds the others back; a window still drawing when the next refresh comes skips it. A pointer's paint stamps pieces at least half the brush long and paints a big piece's rows on several cores (`LaserPaint.Piece`, from 24 rows).

**Switching Diagnostics without touching the PC or phone** (`tools/gp-log.sh`, Git Bash on the PC, for an agent): `pc on|off|save|keep N` sends LOG_CTL (0x7D, unsealed, taken only from 127.x like LINK_TEST_CTL; byte 12 what: 1 Diagnostics, 2 Save, 3 Keep, byte 13 the value), which the Performance page then shows; `phone on|off|save|keep N|status` goes over adb to the phone's `dumpsys`. Each switch stays as set until switched back, the same as tapping it.

**Input log** (`InputRecorder`): its lines go into Diagnostics while it is on, and into `%LOCALAPPDATA%\GyroPhone\logs\input.log` (5 MB, then `input.log.old`) only while a [Link test](#link-test) runs (its script reads that file), for finding stutter after real play. A session that comes up while it is on starts its log at once. Each line has the wall-clock time, then seconds since the session started. While a session is up there is one `sec` line a second (packets, moving packets, lost, late, the latest packet's extra delay, latency p50/p99 and jitter once the phone sent a clock offset, injections, pixels moved, biggest step, slowest receive-to-SendInput, and `lockwait` with who had the lock when gp-rx waited 0.1 ms or more for it; while Diagnostics is on also `delivery[SendInput|driver] n N p50 p99 max over2 unmatched merged [stray]` in ms (n: raw moves matched; unmatched: moves that never showed up, which means lost moves; merged: moves that came inside another raw move; stray: raw moves from GyroPhone that matched nothing): each mouse move from the start of its hand-off to Windows delivering it as raw input, from Diagnostics' delivery probe, below), and one line per event, written when it happens:
- `lost`: 3 or more packets missing from the seq.
- `late`: packets more than 15 ms later than the session's fastest ones of the last 5-10 s (receive time minus phone send time, so no clock sync is needed), one line per stretch; "held up on the way" when the phone sent them on time.
- `phone gap`: the phone sent nothing for over 30 ms (its keepalive is 20 ms) with nothing lost, while input was moving or held.
- `catch-up`: late or lost motion spread out by `MouseCatchUp` instead of landing at once.
- `big move`: 64 px or more in one SendInput.
- `slow hand-off`: over 2 ms from receive to SendInput, with what took the time (each part from 0.05 ms): gp-rx's waits for the `engine lock` and who had it at the longest (`ui`, `watchdog`, `settings save`, `probes`, `pad`, the pad thread taking the newest wish or finishing a plug), time inside the `pad driver` (ViGEm or the DualSense driver) and `SendInput`, `garbage collection` pauses (`GC.GetTotalPauseDuration`) and `the rest` (gp-rx waiting for a CPU, the burst's other packets), e.g. `3.1 ms from receive to SendInput: engine lock 2.6 ms (ui had it), pad driver 0.2 ms, the rest 0.3 ms`. Through the input driver it reads `from receive to input driver:` and names `input driver` in place of `SendInput`.
- `refused`: Windows took fewer events than given.
- `release`: everything let go after 250 ms of silence.
- `session start` / `session end` (with the session's totals and extra-delay percentiles).
At most 10 event lines a second: the rest are counted in that second's `sec` line (`bigmoves N`, "N more events not written"), so a fast flick that moves 64 px every millisecond stays cheap (an event's text is made only when it will be written). The engine queues the lines under its lock and hands them to the log only after letting go of it. Like every log it counts keys and buttons but never names them.

## Performance

The **Performance** page (`PerformancePage`, `Host/Perf`) holds everything the companion measures, and measures only while it is on screen (not on another page, not minimized or closed) or Diagnostics is on. Its aim: debug the phone link and find where drops come from; the game's frames are context for when something odd happens.

- **Link card** (live): the way the phone's packets go, detected from both ends (`LinkPaths`): the phone's side from LINK_INFO's path (**Router Wi-Fi** with band and channel, **Phone hotspot**, **USB cable** direct or tethering, **Ethernet**; the phone's Wi-Fi client on the PC's own Mobile hotspot reads **PC hotspot**) and the PC's adapter on the phone's subnet (its Windows name, such as "Wi-Fi" or "Ethernet"; the Mobile hotspot is the Wi-Fi Direct virtual adapter or 192.168.137.x), such as "Phone hotspot · PC Wi-Fi". Then packets a second, loss, signal and speed (Wi-Fi only), the phone's send rate, round trip and low-latency Wi-Fi; latency p50, p99 and jitter with a graph of the time the page was open; the last 10 seconds as a graph with an orange mark under each second where the link lost or held up packets, paused, or let go of held keys (the input recorder counts the link's seconds while the Performance page is shown, an FPS overlay is on, Diagnostics is on or a link test runs), plus the game's frame times and jumps while an FPS overlay is on; the **Measure buttons** switch ([Latency test](pc-latency-test.md)).
- **Frames**: only the **FPS overlay** ([PC overlays](pc-overlays.md)) watches the game: the frame watch (`FpsHelperSource`) runs while one is added and switched on, and nothing else starts it. It reads (`EtwPresents`) the frames every program shows with Direct3D 9 to 12 from Windows' event tracing (flushed every 100 ms) (the DXGI and D3D9 present events, as PresentMon and the Xbox Game Bar do). It only listens, nothing touches the game, so it is anti-cheat safe. The tracing session is named per Windows user, so two signed-in users' watches never stop each other. While it runs, the input log's `sec` line also gets the game's frames that second, jumps, the worst frame and the game's name.
- **FPS helper**: Windows lets a program start that tracing only with admin rights, and the companion runs without them. So a small separate program, the **FPS helper** (`GyroPhone.FrameHelper`, `GyroPhoneFpsHelper.exe`, native AOT, carried inside the companion's exe), does the tracing. While an FPS overlay is on and the helper isn't set up, the page shows a warning bar (and the overlay "Needs the FPS helper: open Performance"): **Set up FPS helper** asks once for admin rights (`FpsHelperSetup`), copies the helper to `C:\Program Files\GyroPhone` (only administrators can change files there, so nothing can swap it; the copy is checked against the companion's own hash after it lands there), and adds the Windows task **GyroPhone FPS helper**, which starts it as administrator at this user's sign-in without a prompt, and starts it now. From then on GyroPhone never asks again. The helper idles until the companion connects to its pipe (`FrameHelperWire`: one-way, open only to this Windows user, and not to its low-integrity programs such as a sandboxed browser); then it traces and passes each frame's process and time on, and stops when the companion lets go. It takes no commands and opens no process. When the helper isn't running (closed since sign-in), the companion starts its task (no prompt). A companion with a newer helper (`FrameHelperWire.Version`) shows the bar again to update it (one more prompt); companion updates alone don't. Running the companion as administrator, it traces itself (`FrameWatch`) and needs no helper. To remove it: delete the task in Task Scheduler and the `C:\Program Files\GyroPhone` folder.
- **Frames per second**: the frames in the second up to the game's newest frame, by the frames' own times (Windows hands them over in batches, so counting by arrival would jump); 0 once the newest is 1.5 s old.
- **The game**: once a second, the window in front if it shows frames; else the game picked before while it still shows frames; else whichever program shows the most. The companion itself and `dwm` are never picked. "In the background" when it isn't in front.
- **Jump**: a frame at least **2×** the middle (median) of the 60 frames before it and at least **8 ms** longer: one rule at any frame rate. A gap of 1 s or more (a loading screen, the game in the background) isn't a frame; the count starts again after it.
- **Diagnostics card** (more under [Diagnostics](#diagnostics)): the **Diagnostics** switch, **Keep** (1–30 min), **Save** (while on), **Open debug folder** and the **A/B test**, then what it is doing ("On for 4:12, keeping the last 3 min", "Saved: …"). While on, **PC is busy** (a warning) shows while other programs together use 20% of the PC or more, naming the busiest ("java 31%, dotnet 9%"): a build, scan or update running meanwhile causes hitches the link would be blamed for. The game, GyroPhone and the desktop compositor (dwm) don't count; without the FPS overlay the program in front stands for the game. It reads Windows' Process counters (its own process list, no program is opened), once a second, only while this page is shown or Diagnostics is on. A saved record keeps the link's every second, the detected path each second (each change kept: "Router Wi-Fi → Phone hotspot"), and the PC's load.
- **Results**: one row per record, newest first, link first: name (click it for the results page), when, path (detected), lost, late (with the worst delay), phone pauses, let go (releases), bursts (stretches of link trouble: seconds in a row with any, a quiet second between two still joining them), latency (typical · slowest 1%: the middle of the seconds' p50 and of their p99), jitter; then avg fps, 1% low, jumps per minute and worst frame (– without the FPS overlay), CPU (with **⚠ busy N s** in the warning colour when other programs kept the PC busy, the busiest in its tooltip), and driver time with the busiest processor's. With two or more records the best value of lost, late, pauses, bursts, latency, fps, 1% low and jumps is in the accent colour. Only the newest 50 records are kept (`PerfMonitor.MaxRuns`). **Open results** opens `logs\perf\results.html` in the browser, one page, rewritten after every record (`PerfReport`): the same table, then each record with its second-by-second text (folded): a summary, a **Link trouble** table (each burst's clock time, its second of the minute `:ss` to spot a repeating pattern such as :52, its length, lost, late, worst delay, pauses, let go, the game's jumps in it, the phone's longest gap between STATEs, latest send-thread wake and longest send in it or the second before, and the busy programs in it or the second before), then a line per second (`:ss`, link rx, lost, late, worst delay, pauses, releases, latency p50 and p99, jitter | the phone's STATEs and packets sent, failed and slow (2 ms+) sends, longest send, latest wake, longest gap, packets the whole phone sent | frames, fps, worst frame, jumps | CPU, DPC, interrupt, busiest processor | the busy programs that second). The summary warns when the PC was busy, for how long and mostly with what. The phone's numbers come from PHONE_STATS ([protocol](protocol.md)): while Diagnostics is on the PC sets TEST_MODE PHONE_STATS and the phone measures its send thread and sends them each second; otherwise it measures nothing. Each second is placed by the phone's clock, so a report that arrives late still lines up. A phone without it shows "phone: no numbers". **Open folder** opens `logs\perf`, where `runs.jsonl` holds the kept records with their text (rewritten with the newest 50 after each record). Older versions wrote a text file per record; the page still reads those for the records they belong to.

## Diagnostics

The **Diagnostics** switch (Performance page, and the phone's, switched together) logs everything into memory for the last **Keep** minutes; **Save** writes it out. This section is what it measures and how to read it.

**What runs only while Diagnostics is on.** Everything below: the flight records, the stall watch, the setup readings, the phone's PHONE_STATS and its 5 pings a second, the network arrival watch and the A/B test. With it off none of them runs or allocates; the input path checks one reference and moves on. The phone's clock estimate (below) is the one part that always runs: it is part of the link.

**Floor and over the floor.** Lateness used to be measured against an estimate of the phone's clock, which drifted. Now each packet's delay is split in two:
- the **floor**: half the shortest round trip of the last pings, the fastest a packet can cross this link (it needs the clocks' offset only to the extent the ping is symmetric);
- **over the floor**: how much later than the fastest packets of the last 5–10 s this one came. It needs no clock estimate at all, so it is exact, and it is what "late" means in every number below.

`late` counts packets 15 ms+ over the floor, `late3` those 3–15 ms over. Each second keeps a coarse histogram of over-the-floor delays (edges 0.1, 0.2, 0.3, 0.5, 0.75, 1, 1.5, 2, 3, 4, 5, 7.5, 10, 15, 20, 30, 50 ms); a record pools them over every packet, so a busy second (1000 packets) weighs more than a quiet one (50), and splits **moving** seconds (most packets moved something) from **still** ones. `neglat` counts packets whose latency estimate came out below zero (a sign the clock estimate was off; it should stay 0).

**The phone's clock estimate** (`ClockSync`, phone): from the pings, the round trips of the shortest few in each bucket of time, fitted as a line, so the offset follows the two clocks drifting apart instead of jumping. PHONE_STATS carries its best and typical round trip and the drift (ppb).

**Who held a late packet up** (`heldup air N pc N phone N`): each hold-up (a stretch of packets 3 ms+ over the floor) is blamed once, and its packets counted under it: the **phone** when the phone itself paused (the phone times of two packets in it are more than 30 ms apart); else the **PC** when the PC's **stall watch** (`StallWatch`: a thread that wakes every 1 ms at above-normal priority and notes how late it woke; a wake 2 ms+ late is a stall) saw a stall between when the first packet should have come and the last one came; else it was held up on the way (**air**: Wi-Fi, router, adapter, driver). Without the stall watch (an older input program) the line reads "sent on time: held up on the way".

**Hand-offs.** `handoff` is the slowest time this second from a packet's arrival to its input being handed to Windows (SendInput or the pad driver), `slow` the hand-offs over 2 ms, `lockwait` the longest wait for the engine lock, `padonly` the hand-offs of controller-only packets. Event text (the press and link lines) is made off the input path: the input thread stores numbers in a ring, a side thread writes the text.

**Setup.** Each record and save starts with a setup line (`setup: path … · pc adapter … · pc driver … · pc wifi 5 GHz ch 48 · pc power plan … · pc display 165 Hz · pc suspects … · gp … · input program Rust · overlays 2 · phone usb adapter … · phone charging yes · phone battery 81% · phone temp 31.5 °C · …`). The PC side is read by `PcSetupReader` (adapter and its driver version from the registry, link speed or Wi-Fi band, channel, signal and rate, power source, plan and mode, display refresh, and a short list of programs known to disturb input or the link that are running); the phone's comes in PHONE_STATS (`PhoneSetupReader`: battery, charging, battery saver, Doze, thermal status, temperature, Wi-Fi standard and width, USB network adapter). It is checked every 5 s while Diagnostics is on: a change is logged (`setup changed: pc wifi 5 GHz ch 48 → 5 GHz ch 100`); battery level, temperature, Wi-Fi signal and rate change all the time and are left out of those lines. **Floor shift warning**: `FloorBook` (`logs\perf\floors.json`) keeps the floor seen on each link setup (path, adapters, drivers, Wi-Fi, input program); a record whose floor is 0.15 ms and 25% off the last one on the same setup gets "⚠ floor … on the same setup" in Results: something changed that the setup line doesn't show, so it can't be compared with the earlier ones.

**Results columns** (besides the ones under Performance): **Floor** (⚠ when shifted), **Over the floor** (p50 / p99, all packets, and moving vs still p99 in the tooltip), **Hand-offs** (slow ones per 10,000 packets · slowest), **Held up** (air / PC / phone). Each record's card shows its setup and changes.

**Flight record.** A per-packet record on both sides, in a ring made when Diagnostics comes on (66,000 entries a minute of Keep, so a 30-minute Keep is about 63 MB on the PC; nothing is allocated while it is off). The input thread only stores numbers into it. A Save writes it beside the text save (newest 5 kept):
- PC, `Documents\GyroPhone\Debug\pc-<time>-flight.bin` (`FlightRecorder`, and `flight.rs` in the Rust input program, same format): per accepted STATE its arrival (QueryPerformanceCounter µs), the phone time it carries, how much over the floor, the hand-off time, lock wait, time in the drivers and flags (moving, active, lost before it, controller only, refused by Windows, handed off).
- Phone, `files/debug/phone-<time>-flight.bin` (`FlightRing`): per STATE sent its time, seq, the phone time it carries, the age of the newest gyro sample in it, how long the send took, how late the send thread woke and flags (keys or buttons changed, keepalive, failed, carried a new gyro sample). `tools/debug-collect.sh` pulls it with the text save.
Both files: a 40-byte header ("GPFLIGHT" or "GPFLPHON", version 1, entry size 32, count, the clock and the Unix time in ms at the save), then the entries, oldest first. The two pair by the phone time each STATE carries.

**Network arrival** (Windows). While Diagnostics is on, the FPS helper (or the companion itself when it runs as administrator) also listens to Windows' own network events (`EtwNetArrivals`: the Microsoft-Windows-Kernel-Network provider's "UDP received" events, filtered to those two events and to GP's port 47800) and passes each arrival's time on a second pipe (`FrameHelperWire`, version 3). The companion keeps them in a ring like the flight record's (`NetArrivalWatch`) and a Save writes `pc-<time>-net.bin` (header "GPNETARR", entries of arrival QPC µs, bytes, sender's port). Paired with the flight record it splits each late packet into "came late to the PC" and "waited in the PC before the input program took it". Every UDP datagram the PC receives logs one small event while it runs, so it runs only with Diagnostics. It covers Wi-Fi and Ethernet; the USB cable link doesn't arrive as UDP and isn't seen. The helper changed, so it asks to be set up again once (one admin prompt).

**A/B test** (Diagnostics card, while on). Switches one thing back and forth every 1–10 min (**Switch every**, default 3) while you play: **A/B input program** (Rust and C#; switching restarts the input program, so anything held is let go for a moment) or **A/B overlays** (shown and hidden). Each switch is marked in the log (`ab: phase 3 A: overlays shown`), the status line shows the phase and the time to the next switch, and **Stop A/B** (or Diagnostics going off) puts it back as it was at the start. A and B are then measured on the same day, Wi-Fi and game. Play for at least 4 phases, then Save.

**Comparing runs** (`tools/diag/gpdiag.py`, Python 3.8+, no packages; its tests: `python -m unittest discover tools/diag`):
- `summary <pc-save.txt>…`: one run's numbers, all / moving / still.
- `compare <A saves> -- <B saves>`: the setup differences first, then each rate per 10,000 packets with a likely range. Slow hand-offs and late packets come in clusters, so the range resamples whole minutes (a bootstrap over minute blocks); two runs whose ranges overlap show "no clear difference". With under 5 minutes a run it says the ranges are rough.
- `ab <save>`: splits a save made during an A/B test by its marks (leaving out the first 10 s after each switch) and compares A with B the same way.
- `flight <pc-…-flight.bin> [phone-…-flight.bin] [pc-…-net.bin]`: per-packet percentiles, packets that arrived bunched, and with the phone's record which late packets left the phone late; with the network record how long packets waited in the PC.

**Delivery probe** (Diagnostics, how to read it). It reads raw mouse input in the background on its own thread and matches what arrives to GP's moves by their sums (`DeliveryMatcher`). Windows 11 hands a background reader a device's moves merged, about 125 times a second, so one raw move is the sum of several of GP's: the time is measured from the **newest** of them, and the older ones in it waited longer than it shows (`merged` counts them). Two runs of moves with the same sum close together can be paired with the wrong one. A game in front gets every move one by one, so the probe shows a background reader's merged timing, not exactly what the game sees; the **Delivery test** window, which reads in front like a game, is the exact one.


## Link test

Finds out why phone packets get lost or held up, without anyone playing: `tools/link-test.sh [minutes] [--open]` (Git Bash on the PC, default 10 minutes; `--open` starts GyroPhone on the phone over adb first). It sends LINK_TEST_CTL to the companion on loopback; the companion logs `link test started` (companion.log and input.log, which it writes only during a link test) and sets TEST_MODE LINK_TEST until the time is up or it is stopped. The phone then sends, in place of its real input, STATEs with nothing held and the mouse totals sweeping 3 counts a packet (`StateFrame.fillLinkTest`), marked LINK_TEST, so it sends at its full rate; the pad shows **Link test running** over it and keeps the screen on. The companion handles them like any STATE (seq, loss, lateness, catch-up, input log) but never moves, presses or submits anything from them. Meanwhile the script records, when the phone is on adb, logcat (all buffers) and `cmd wifi status` every 2 s into files on the phone (`/data/local/tmp/gp-link-test/<time>/`, pulled after the test and left there, so nothing streams over the link being tested), and `dumpsys wifi` / `wifiscanner` before and after. It reads the phone's clock over adb 7 times before and after; the analyser uses the reading with the shortest round trip and prints its error and the drift. Then it copies input.log and companion.log and runs `tools/link-test-analyze.py`, which places each event at its exact time (the log line's second column, not the time the line was written, which for a hold-up is its end), groups the dropouts, says how regularly they come (and at which second of the minute) and lists the phone's Wi-Fi-related log lines from 1.5 s before to 0.5 s after each one. Everything goes to `build/link-test/<time>/` (`report.txt`).

## Watcher

`GyroPhoneCompanion.exe --watch` (`Watcher`): no window, no tray. While the companion is off it holds UDP 47800; the first DISCOVER from a known phone (by phone id or key id) makes it free the port and start the installed companion (with `--woken`), at most once per gap. It never binds while a companion runs or is starting (the companion takes its lock first thing), nor for up to 30 s after it started one that hasn't taken its lock yet. It waits on the socket, the stop switch and the companion's yield request together, so it lets go of the port within milliseconds. Opted out of power throttling. Started at login by the `GyroPhoneWatcher` Run entry; on and off with **Start when my phone appears** on the App page. DISCOVER is not authenticated, so a spoofer can only start the companion; connecting still needs the key.

**Companion start and the port.** The input process owns the port. When a watcher runs, the input process asks it to yield the port before its first bind. If the port is still taken, a gp-bind thread keeps trying, off the UI thread, every 25 ms for 5 s (the tray says Starting…), then every second for as long as the app runs (Home then shows the port as in use by another program), asking the watcher each time; the server, watchdog, cable link, overlays and shortcuts start once it binds.

**Locked files at start.** settings.json and host.key, when another program holds them (a scanner or backup tool), are retried for 3 s on a start by hand and 15 s on a start by the watcher (`--woken`) or an update. A settings.json still locked stops the start (starting on defaults would overwrite the pairings). A host.key still locked leaves key file and QR code pairing off only until a background retry (every 5 s) reads it; meanwhile Home shows it as a problem.
