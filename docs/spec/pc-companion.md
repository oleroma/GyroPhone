# PC: companion app and tray

The Windows companion (`GyroPhoneCompanion.exe`) receives the phone's Wi-Fi/USB link and turns it into a virtual game pad, keyboard and mouse, and draws the overlays. Bluetooth needs no companion. Projects in `companion/src/`:

| Project | What it is |
|---|---|
| `GyroPhone.Protocol` | Wire format, crypto, STATE to pad and SendInput mapping, gyro math port. Cross-platform, unit tested. |
| `GyroPhone.Host` | The protocol engine (`HostEngine`), UDP server, sessions, pairing, settings, key files, link stats, overlay pose. Cross-platform; all I/O behind interfaces in `Abstractions/`. |
| `GyroPhone.Windows` | Windows sinks and probes: SendInput, ViGEm, XInput PC pad, AOA USB, firewall, DPAPI, autostart, MMCSS, power QoS, logs. |
| `GyroPhone.Tray` | The exe: tray icon and menu, overlays, watcher, updater, Debug window. WinForms + Direct2D (Vortice). |
| `GyroPhone.Ui` | The WPF main window and pairing window, reached through `ICompanion`. |
| `GyroPhone.Headless` | A console host for Linux/testing (`--pair`, `--no-vigem`, `--latency-csv`). Not shipped. |

.NET 8, published self-contained, single file, win-x64.

## Threads and timing

- **gp-rx** (`UdpHostServer`): the one UDP socket on port **47800**. Blocks in ReceiveFrom, drains the backlog into `HostEngine.OnDatagram`, then `Flush` injects once, so a burst of STATEs makes one injection. A STATE whose keys or buttons differ from the one before it injects that earlier one first, so no press is lost; a pad button pressed and released inside one burst stays visible for 20 ms for polling games. Registered with MMCSS ("Games", high) and opted out of power throttling (`Mmcss`, `PowerQos`). No timer resolution change. While a lost or late stretch of mouse motion catches up it also wakes every millisecond without packets to move it on: on Windows by waiting on the socket's read event and a high-resolution waitable timer together (`ExactCatchUpWait`; WSAEventSelect for the wait only, the socket stays blocking otherwise), since a plain socket.Poll timeout only ends on the 15.6 ms system tick; a datagram still wakes it at once.
- **gp-watchdog** (`Watchdog`): its own thread at AboveNormal priority, ticking every 50 ms on a high-resolution waitable timer, for `HostEngine.OnTick`: releases everything after **250 ms** without a STATE, drops a session after 10 s, expires pending sessions (2 s), runs pairing timers and sends HOST_STATUS once a second. The tick does only in-memory work. Environment probes (1 Hz) go to the thread pool.
- **gp-keepawake** (`Watchdog`): an AboveNormal thread that sends the phone a tiny sealed KEEP_AWAKE every **10 ms** while a session runs over Wi-Fi (not over USB, Ethernet or loopback; always on, no setting). A Wi-Fi client in power save wakes only at each beacon, about every 100 ms, so while the phone sends little (held still) its packets would reach the PC in 100 ms batches; the steady traffic keeps the PC's radio awake. It takes no engine lock.
- **gp-save** (`Watchdog`): a BelowNormal writer thread that, every 500 ms, writes the held-keys marker if the held set changed and settings if anything changed (all changes since its last turn in one write; a failed write is retried after 1 s). A slow disk or a virus scan never holds up a tick, and never runs on gp-rx.
- **gp-usb-rx / gp-usb-tx** (`UsbBridge`) for the direct cable: every packet passes through them before gp-rx, so they get the same MMCSS ("Games", high) registration and power-throttling opt-out.
- **Overlay pacer** and the UI thread ([Overlays](pc-overlays.md)).
- **gp-press-listen** (`RawInputListener`): only while the phone's "Press a key" listens (CAPTURE): a hidden message-only window reading the keyboard and mouse through raw input (RIDEV_INPUTSINK). It only reads, so every key and click still reaches Windows and the game; keyboard input with no device behind it (SendInput, ours too) is skipped. The PC controller reader (`XInputPcPad`) runs meanwhile too. `PressCapture` turns both into CAPTURED on the watchdog's tick. Each time it starts, the tray shows a Windows notification, **"Press a key or button"**, so you know keys, mouse buttons and controller buttons on the PC count too (`HostSnapshot.Capturing`). The App page's **Press a key** card has **Use this PC's keys for Press a key** (on by default; off, CAPTURE is ignored and the PC is never read, and turning it off while the phone listens stops at once; `HostSettings.PressKeyListen`) and under it **Notify when the phone listens for a key** (on by default; `PressKeyNotice`). Mouse buttons count even with no device behind them, since a laptop's precision touchpad sends its clicks that way (GyroPhone sends no clicks while the phone listens); keys with no device (SendInput) are still skipped. The latency test window reads raw mouse input as well; a process has one raw input target per device kind, so if both run at once its bar stops until it is opened again.
- **gp-log** (`FileLog`, Normal priority): writes the log files. `Write` only puts the line in a lock-free queue and wakes it, so no thread ever waits on it.

All engine state is under one lock, which gp-rx takes for every packet and Flush. So that a thread Windows pauses while holding it never keeps gp-rx waiting, everything read many times a second is read without it: when a locked call ends, the engine copies what changed into a published view (`OverlayView`, a sequence lock: readers copy and retry if a write came in between, the writer never waits), and the overlay windows (newest OVERLAY and layout, each window's pose, "Fade when phone rests", the Fire and Aim displays' outputs, Connected), the held-keys marker and the catch-up flag read only that. The PC controller's state comes from its reader thread's own published copy (`IPcPad.Peek`). An OVERLAY that comes in a burst with a STATE is published after the Flush, and the laser outputs after the hand-off, so publishing never delays input. `Snapshot` (tray and main window) only copies plain values under the lock (the paired phones list is kept ready), and settings are turned into JSON after the lock is let go (a change made meanwhile is saved on the next tick). The pad driver and SendInput calls stay under the lock, as they decide what the engine counts as held. Engine callbacks only post to the UI thread.

## Sessions and safety

- One **active session**; a new one replaces it only when its first valid STATE arrives (`SessionManager`), and the old phone gets HOST_BYE REPLACED.
- **Release-all** on silence (250 ms), session end, Pause, workstation lock or suspend, exit, and session switch.
- **Crash safety** (`HeldKeysMarker`): while anything is held, `%LOCALAPPDATA%\GyroPhone\held.json` lists it (written by gp-save within half a second of a change, and on exit); the next start releases what it lists and deletes it.
- **UIPI**: when an elevated window is in front or the secure desktop is up, SendInput drops events; the engine notices, and once input goes through again re-sends the ups and then the downs of what is held, so Windows' key state matches. Home warns, with **Restart as administrator**. The companion only checks its own token, never opens other processes (anti-cheat logs that).
- **Pause input** (tray, Gamepad page): releases everything; STATEs keep updating the baseline but inject nothing.

## Tray

`TrayApp`. Left click opens the main window (App page: or pairs a new phone). The right-click menu is short, the everyday switches only:

- the version, a status line, and a problems line that opens Home;
- **Open GyroPhone**, **Pause input**;
- **Gamepad output** ▸ Xbox 360 (default) / DualShock 4 / Off (keyboard and mouse only);
- **Overlays** ▸ one switch per window, Hide all overlays (Ctrl+Alt+O), Edit: drag the windows to move and resize (Ctrl+Alt+E), Level all: as held now shows face-on (Ctrl+Alt+R), Overlay settings…;
- **Pair new phone…**;
- **Exit**.

## Main window

`GyroPhone.Ui/MainWindow.cs`, a sidebar of pages, refreshed twice a second. A page is built the first time it is shown, only the page on screen is refreshed, and Performance's Latency test reads its result files off the UI thread. A change made on a page (a slider step, a toggle) refreshes only that page at once; the tray and Home follow 250 ms after the changes stop, and an overlay draws the change at its next frame.

- **Home**: a warning bar per problem with its fix (no ViGEmBus, firewall, Public network while no phone is seen, input blocked by an elevated window…), then cards: phone, link (only the way its packets go, such as "Phone hotspot · PC Wi-Fi"), gamepad (output, pause); full status under Details. Link numbers and latency are on Performance.
- **Phones**: Pair new phone, paired phones (each with Forget), this PC's key.
- **Gamepad**: output Xbox 360 / DualShock 4 / Off, Pause, the ViGEmBus driver state and Retry.
- **Overlays**: see [Overlays](pc-overlays.md).
- **Connection**: network category, firewall and USB checks with their fixes, the USB cable (direct cable on/off, default on), the server's port and addresses.
- **Performance**: everything measured and every speed setting: the phone link live with latency, link tests to compare ways of connecting, the video Latency test (see [Performance](#performance)), Mouse (**Catch-up time**: Off / 8 / 16 / 32 ms, default 16, `HostSettings.CatchUpMs`; the longest a lost or late stretch of mouse motion is spread over, Off = the old one-step jump), and Debug (**Record input log**, default on; **Overlay timing log**, default on; Open log folder, Debug window…).
- **App**: Startup (Start with Windows, default off; **Start when my phone appears**, the watcher), Tray icon click (Opens this window / Pairs a new phone), Press a key, About (version).

**Scrolling** (`WheelScroll`, every window): the wheel and the touchpad scroll like a web browser. Each wheel message moves the page in proportion to its size: a whole notch is 100 px at Windows' usual 3 lines a notch (as Chrome; it follows that setting, and "one screen at a time" scrolls most of a screen), eased in over a few frames; a touchpad's small steps move it at once, so the page follows the fingers. The innermost scrollable area under the pointer that can still move that way takes it, so a table that scrolls only sideways (Performance's Results) passes the page's scrolling on, and a list at its end passes it to the page. Shift + wheel and the touchpad's sideways swipe scroll sideways. Item-based lists keep WPF's own scrolling.

**Pairing window** (`PairWindow`): a QR code for the phone's Scan QR code (a one-time token, renewed when it expires, gone when the window closes; holds up to four of this PC's IPv4 addresses), and for code pairing the PC's name, addresses, port and the pairing countdown, then "Pair <phone>? Code 123 456" with **Allow** / **Deny**. On first run with nothing paired the pairing window opens by itself.

**Debug window** (`DebugForm`, from Performance › Debug): the link as the PC sees it, what the game is given now, and the newest debug events at 4 Hz; **Save last 30 s**. The engine logs only while it is open or the phone's debug tools are on. A phone-side Record also saves the PC's (LINK_INFO save counter).

**Overlay drawing threads**: the pacer (`OverlayPacer`) wakes every open overlay window at each screen refresh, and each window draws on a thread of its own (`OverlayForm.Signal`, "overlay <id>"), so windows draw side by side and a heavy one (a pointer's paint) never holds the others back; a window still drawing when the next refresh comes skips it. A pointer's paint stamps pieces at least half the brush long and paints a big piece's rows on several cores (`LaserPaint.Piece`, from 24 rows).

**Overlay timing log** (Performance › Debug, on by default, `HostSettings.OverlayTimingLog`): each open overlay's draw times (average, longest, frames a second, GPU or CPU) in `companion.log`, one line a second while any overlay draws and one every 30 s while they are idle; off, none. The Performance page's **Debug** card holds every log and debug tool: Record input log, Overlay timing log, the log folder and the Debug window.

**Input log** (`InputRecorder`; **Record input log** in Performance › Debug, on by default, `HostSettings.InputLog`): `%LOCALAPPDATA%\GyroPhone\logs\input.log` (5 MB, then `input.log.old`), for finding stutter after real play. Turning it off ends the session's log at once; turning it on starts one for the session already up. Each line has the wall-clock time, then seconds since the session started. While a session is up there is one `sec` line a second (packets, moving packets, lost, late, the latest packet's extra delay, latency p50/p99 and jitter once the phone sent a clock offset, injections, pixels moved, biggest step, slowest receive-to-SendInput, and `lockwait` with who had the lock when gp-rx waited 0.1 ms or more for it), and one line per event, written when it happens:
- `lost`: 3 or more packets missing from the seq.
- `late`: packets more than 15 ms later than the session's fastest ones of the last 5-10 s (receive time minus phone send time, so no clock sync is needed), one line per stretch; "held up on the way" when the phone sent them on time.
- `phone gap`: the phone sent nothing for over 30 ms (its keepalive is 20 ms) with nothing lost, while input was moving or held.
- `catch-up`: late or lost motion spread out by `MouseCatchUp` instead of landing at once.
- `big move`: 64 px or more in one SendInput.
- `slow hand-off`: over 2 ms from receive to SendInput, with what took the time (each part from 0.05 ms): gp-rx's waits for the `engine lock` and who had it at the longest (`ui`, `watchdog`, `settings save`, `probes`, `pad`, the pad thread taking the newest wish or finishing a plug), time inside the `pad driver` (ViGEm or the DualSense driver) and `SendInput`, `garbage collection` pauses (`GC.GetTotalPauseDuration`) and `the rest` (gp-rx waiting for a CPU, the burst's other packets), e.g. `3.1 ms from receive to SendInput: engine lock 2.6 ms (ui had it), pad driver 0.2 ms, the rest 0.3 ms`.
- `refused`: Windows took fewer events than given.
- `release`: everything let go after 250 ms of silence.
- `session start` / `session end` (with the session's totals and extra-delay percentiles).
At most 10 event lines a second: the rest are counted in that second's `sec` line (`bigmoves N`, "N more events not written"), so a fast flick that moves 64 px every millisecond stays cheap (an event's text is made only when it will be written). The engine queues the lines under its lock and hands them to the log only after letting go of it. Like every log it counts keys and buttons but never names them.

## Performance

The **Performance** page (`PerformancePage`, `Host/Perf`) holds everything the companion measures, and measures only while it is on screen (not on another page, not minimized or closed) or a link test records. Its aim: debug the phone link and find where drops come from; the game's frames are context for when something odd happens.

- **Link card** (live): the way the phone's packets go, detected from both ends (`LinkPaths`): the phone's side from LINK_INFO's path (**Router Wi-Fi** with band and channel, **Phone hotspot**, **USB cable** direct or tethering, **Ethernet**; the phone's Wi-Fi client on the PC's own Mobile hotspot reads **PC hotspot**) and the PC's adapter on the phone's subnet (its Windows name, such as "Wi-Fi" or "Ethernet"; the Mobile hotspot is the Wi-Fi Direct virtual adapter or 192.168.137.x), such as "Phone hotspot · PC Wi-Fi". Then packets a second, loss, signal and speed (Wi-Fi only), the phone's send rate, round trip and low-latency Wi-Fi; latency p50, p99 and jitter with a graph of the time the page was open; the last 10 seconds as a graph with an orange mark under each second where the link lost or held up packets, paused, or let go of held keys (from the input log's `sec` line, so **Record input log** must be on), plus the game's frame times and jumps while an FPS overlay is on; the **Measure buttons** switch ([Latency test](pc-latency-test.md)).
- **Frames**: only the **FPS overlay** ([PC overlays](pc-overlays.md)) watches the game: the frame watch (`FpsHelperSource`) runs while one is added and switched on, and nothing else starts it. It reads (`EtwPresents`) the frames every program shows with Direct3D 9 to 12 from Windows' event tracing (flushed every 100 ms) (the DXGI and D3D9 present events, as PresentMon and the Xbox Game Bar do). It only listens, nothing touches the game, so it is anti-cheat safe. While it runs, the input log's `sec` line also gets the game's frames that second, jumps, the worst frame and the game's name.
- **FPS helper**: Windows lets a program start that tracing only with admin rights, and the companion runs without them. So a small separate program, the **FPS helper** (`GyroPhone.FrameHelper`, `GyroPhoneFpsHelper.exe`, native AOT, carried inside the companion's exe), does the tracing. While an FPS overlay is on and the helper isn't set up, the page shows a warning bar (and the overlay "Needs the FPS helper: open Performance"): **Set up FPS helper** asks once for admin rights (`FpsHelperSetup`), copies the helper to `C:\Program Files\GyroPhone` (only administrators can change files there, so nothing can swap it; the copy is checked against the companion's own hash after it lands there), and adds the Windows task **GyroPhone FPS helper**, which starts it as administrator at this user's sign-in without a prompt, and starts it now. From then on GyroPhone never asks again. The helper idles until the companion connects to its pipe (`FrameHelperWire`: one-way, open only to this Windows user); then it traces and passes each frame's process and time on, and stops when the companion lets go. It takes no commands and opens no process. When the helper isn't running (closed since sign-in), the companion starts its task (no prompt). A companion with a newer helper (`FrameHelperWire.Version`) shows the bar again to update it (one more prompt); companion updates alone don't. Running the companion as administrator, it traces itself (`FrameWatch`) and needs no helper. To remove it: delete the task in Task Scheduler and the `C:\Program Files\GyroPhone` folder.
- **Frames per second**: the frames in the second up to the game's newest frame, by the frames' own times (Windows hands them over in batches, so counting by arrival would jump); 0 once the newest is 1.5 s old.
- **The game**: once a second, the window in front if it shows frames; else the game picked before while it still shows frames; else whichever program shows the most. The companion itself and `dwm` are never picked. "In the background" when it isn't in front.
- **Jump**: a frame at least **2×** the middle (median) of the 60 frames before it and at least **8 ms** longer: one rule at any frame rate. A gap of 1 s or more (a loading screen, the game in the background) isn't a frame; the count starts again after it.
- **Record test** (a link test): a **Setup** pick (Router / Phone hotspot / PC hotspot / Wired (USB) / Ethernet) that fills in the **Name** (which starts as the setup detected now; type your own, such as "Overlays off"), a **Length** (3 / 5 / 10 min, default 3, or Until I stop), **Record** / **Stop**. Under them the detected path, with a warning when a picked Setup isn't the one detected. Below it, **PC is busy** (a warning) while other programs together use 20% of the PC or more, naming the busiest ("java 31%, dotnet 9%"): a build, scan or update running during a test causes hitches it would blame on the link. The game, GyroPhone and the desktop compositor (dwm) don't count; without the FPS overlay the program in front stands for the game. It reads Windows' Process counters (its own process list, no program is opened), once a second, only while this page is shown or a record runs. It needs no frame watch and no permission. **Record** closes the main window (so its drawing costs nothing during the test); the record goes on from the tray until its time is up. Opening the window ends it early (saved as far as it got), so the window's drawing never gets into a record; it opens on Performance with the record at the top of Results. When a record starts, and when it ends (its time is up, **Stop**, or the window opens), the connected phone buzzes twice and beeps twice (at its notification volume), whatever the output mode. A record keeps the link's every second, the detected path once a second (each change kept: "Router Wi-Fi → Phone hotspot"), the PC's load, and, while an FPS overlay is on, the game's frames while it is in front, from 3 s after it came there (switching windows makes hitches of its own).
- **Results**: one row per record, newest first, link first: name (click it for the results page), when, path (detected), lost, late (with the worst delay), phone pauses, let go (releases), bursts (stretches of link trouble: seconds in a row with any, a quiet second between two still joining them), latency (typical · slowest 1%: the middle of the seconds' p50 and of their p99), jitter; then avg fps, 1% low, jumps per minute and worst frame (– without the FPS overlay), CPU (with **⚠ busy N s** in the warning colour when other programs kept the PC busy, the busiest in its tooltip), and driver time with the busiest processor's. With two or more records the best value of lost, late, pauses, bursts, latency, fps, 1% low and jumps is in the accent colour. Only the newest 50 records are kept (`PerfMonitor.MaxRuns`). **Open results** opens `logs\perf\results.html` in the browser, one page like the latency test's, rewritten after every record (`PerfReport`): the same table, then each record with its second-by-second text (folded): a summary, a **Link trouble** table (each burst's clock time, its second of the minute `:ss` to spot a repeating pattern such as :52, its length, lost, late, worst delay, pauses, let go, the game's jumps in it, the phone's longest gap between STATEs, latest send-thread wake and longest send in it or the second before, and the busy programs in it or the second before), then a line per second (`:ss`, link rx, lost, late, worst delay, pauses, releases, latency p50 and p99, jitter | the phone's STATEs and packets sent, failed and slow (2 ms+) sends, longest send, latest wake, longest gap, packets the whole phone sent | frames, fps, worst frame, jumps | CPU, DPC, interrupt, busiest processor | the busy programs that second). The summary warns when the PC was busy, for how long and mostly with what. The phone's numbers come from PHONE_STATS ([protocol](protocol.md)): while a record runs the PC sets TEST_MODE PHONE_STATS and the phone measures its send thread and sends them each second; outside a record it measures nothing. Each second is placed by the phone's clock, so a report that arrives late still lines up. A phone without it shows "phone: no numbers". **Open folder** opens `logs\perf`, where `runs.jsonl` holds the kept records with their text (rewritten with the newest 50 after each record). Older versions wrote a text file per record; the page still reads those for the records they belong to.
- **Latency test**: the video latency test, as a part of this page ([Latency test](pc-latency-test.md)).

## Link test

Finds out why phone packets get lost or held up, without anyone playing: `tools/link-test.sh [minutes] [--open]` (Git Bash on the PC, default 10 minutes; `--open` starts GyroPhone on the phone over adb first). It sends LINK_TEST_CTL to the companion on loopback; the companion logs `link test started` (companion.log and input.log) and sets TEST_MODE LINK_TEST until the time is up or it is stopped. The phone then sends, in place of its real input, STATEs with nothing held and the mouse totals sweeping 3 counts a packet (`StateFrame.fillLinkTest`), marked LINK_TEST, so it sends at its full rate; the pad shows **Link test running** over it and keeps the screen on. The companion handles them like any STATE (seq, loss, lateness, catch-up, input log) but never moves, presses or submits anything from them. Meanwhile the script records, when the phone is on adb, logcat (all buffers), `cmd wifi status` every 2 s and `dumpsys wifi` / `wifiscanner` before and after, then copies input.log and companion.log and runs `tools/link-test-analyze.py`, which groups the dropouts, says how regularly they come (and at which second of the minute) and lists the phone's Wi-Fi-related log lines from 1.5 s before to 0.5 s after each one. Everything goes to `build/link-test/<time>/` (`report.txt`).

## Watcher

`GyroPhoneCompanion.exe --watch` (`Watcher`): no window, no tray. While the companion is off it holds UDP 47800; the first DISCOVER from a known phone (by phone id or key id) makes it free the port and start the installed companion (with `--woken`), at most once per gap. It never binds while a companion runs or is starting (the companion takes its lock first thing), nor for up to 30 s after it started one that hasn't taken its lock yet. It waits on the socket, the stop switch and the companion's yield request together, so it lets go of the port within milliseconds. Opted out of power throttling. Started at login by the `GyroPhoneWatcher` Run entry; on and off with **Start when my phone appears** on the App page. DISCOVER is not authenticated, so a spoofer can only start the companion; connecting still needs the key.

**Companion start and the port.** When a watcher runs, the companion asks it to yield the port before its first bind. If the port is still taken, a gp-bind thread keeps trying, off the UI thread, every 25 ms for 5 s (the tray says Starting…), then every second for as long as the app runs (Home then shows the port as in use by another program), asking the watcher each time; the server, watchdog, cable link, overlays and shortcuts start once it binds.

**Locked files at start.** settings.json and host.key, when another program holds them (a scanner or backup tool), are retried for 3 s on a start by hand and 15 s on a start by the watcher (`--woken`) or an update. A settings.json still locked stops the start (starting on defaults would overwrite the pairings). A host.key still locked leaves key file and QR code pairing off only until a background retry (every 5 s) reads it; meanwhile Home shows it as a problem.
